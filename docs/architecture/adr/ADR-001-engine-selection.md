# ADR-001 · 引擎选型与仿真核边界

- **状态**：**待用户拍板**（本条不生效，实现不得启动）
- **日期**：Phase 3 · PHASE3-001
- **决策人**：engineering-lead（程基岩）提出 → 主理人游承峰拍板
- **影响面**：全部代码仓库、构建管线、CI、工具链、招人与工期
- **相关**：ADR-002（RNG）、ADR-003（离屏 LOD）、ADR-005（定点数）、`06-consistency-review.md §七-A`

## 1. 背景（Context）

《枯水期》Core 的技术需求不是"做一个开放世界 RPG"，而是"做一个**可逐位复现、可导出证据、可在低配机上跑完整社区模拟**的开放世界 RPG"。约束清单（全部来自已拍板的设计文档与任务硬约束）：

| # | 约束 | 出处 | 对引擎的含义 |
|---|---|---|---|
| K1 | 逐位确定性：`worldHash` 每 60 tick 比对，两次运行须**逐位相同** | S0 §C3 | 仿真不得依赖引擎的浮点、随机数、deltaTime、线程调度 |
| K2 | 禁 `double` 与超越函数（sin/exp），三角函数走查表 + 定点 | S0 §C7-3 | 引擎数学库必须可绕过 |
| K3 | 判定必须在固定 tick 发起，**禁在渲染帧发起** | S0 §C2 红线④ | 引擎帧循环不得驱动判定 |
| K4 | 仿真（非渲染）≤6ms/帧；场内实体 ≤120，full-behavior ≤32 | Core 验收 5 | 仿真要能被单独剖分与压测 |
| K5 | 目标机 GTX 1060 6GB / 16GB RAM / SATA SSD / 1080p，2×2km、第三人称近视角 | 任务硬约束 | 渲染压力低，重型管线（Nanite/Lumen）无收益 |
| K6 | C8 进 Core：**调度可视化面板 + 归因链导出 + 固定种子确定性重放** | 概念文档 C8 | 工具链是一等公民，不是外挂 |
| K7 | 10 日 save/load 差异 ≤5%，需 headless 批量重放做回归 | Core 验收 6 | 仿真必须能脱离渲染独立运行 |
| K8 | 小团队、Core 期禁止新增系统 | 概念文档红线 | 迭代速度与可维护性 > 画面上限 |

**关键洞察（本 ADR 的分析支点）**：K1/K2/K3 共同推出一条架构结论——**确定性仿真必须是"引擎无关的纯数据模块"**。一旦把仿真写进引擎的 `MonoBehaviour`/`Node`/`Actor` 生命周期，就会被引擎的 deltaTime、帧率、对象遍历顺序、物理步进顺序污染，K1 立刻崩塌。而 K7 又要求这个模块能在 CI 里 headless 跑 10 日（14400 tick）。

因此真正要拍板的**不是"用哪个引擎"**，而是两件事：

- **Q1**：仿真核是否做成一个**独立于引擎的库**（下称 `simcore`）？
- **Q2**：表现层用哪个引擎？

---

## 2. 备选方案（Options）

### 方案 A · Unity 6（LTS）+ C# 全栈
- 优点：工具链最成熟（Profiler / Addressables / UI Toolkit / Burst+Jobs）；C# 生态与招人容易；Burst 可给仿真加速且提供 `float` 严格模式。
- 缺点：C# 浮点在不同构建/平台不保证逐位一致（本项目验收是**同机同构建重放**，可接受，但埋雷）；IL2CPP 打包慢；引擎本体重（空场景开销高，GTX 1060 上留给我们的渲染预算更少）；许可与体积成本。
- 对 K1：需严格隔离 sim 到 Burst job 或 C++ 插件，否则难保证。

### 方案 B · Godot 4（.NET 版）+ C# 全栈
- 优点：MIT 许可、无分成、启动/迭代极快；运行时轻量，**对 GTX 1060 最友好**；`Node` 树简单可控。
- 缺点：3D 渲染与 LOD 工具链弱于 Unity（本项目 2×2km 近视角、规模小，风险低）；Profiler 与 Addressables 等价物需自建；生态与招人弱于 Unity。
- 对 K1：同 A，仍需隔离。

### 方案 C · Unreal 5
- 优点：渲染与工具最强；GAS/Replication/UMG 现成。
- 缺点：**与 K5 直接冲突**（Nanite/Lumen 在 GTX 1060 上不可用于生产，全关后又回到"为什么不用更轻的引擎"）；C++ 迭代慢、蓝图/C++ 双轨治理成本高；引擎浮点与线程模型最不透明，K1 最难保证；小团队负担最大。
- 判定：**不推荐**（成本结构与本项目不匹配，非技术否定）。

### 方案 D · 自研仿真核 + 自研/极简渲染层
- 优点：确定性完全可控；无引擎负债。
- 缺点：需自建渲染、导航、UI、资源管线、编辑器——**Core 期做不起**，违反 K8。

### **方案 E（推荐）· `simcore`（C++20 静态库，引擎无关）+ Godot 4 表现层**

结构：

```
┌─────────────────────────────────────────────────────────────┐
│ L4 工具链      headless CLI / 重放器 / 归因导出 / 面板后端   │  ← 只链 simcore
├─────────────────────────────────────────────────────────────┤
│ L3 表现层      Godot 4（渲染 / 动画 / 导航 / UI / 输入）      │  ← 只链 simcore
├─────────────────────────────────────────────────────────────┤
│ L2 系统层      S0·B 时钟 / S0·C 确定性 / S1..S7               │  ← 全在 simcore 内
├─────────────────────────────────────────────────────────────┤
│ L1 仿真核      Fixed / RngStream / EventBus / WriteQueue /    │
│                DaySnapshot / BoundaryScheduler / SaveGame     │
├─────────────────────────────────────────────────────────────┤
│ L0 平台        C++20 / 单线程 / 固定编译选项 / 无引擎头       │
└─────────────────────────────────────────────────────────────┘
```

- `simcore` 暴露 **C ABI**（`extern "C"`），零引擎依赖、零 STL 容器跨界、零异常跨界。
- Godot 侧用 **GDExtension（C++）薄封装**把 `simcore` 挂成单例；表现层每帧调用 `simcore_advance(dtRealSec)` 拿插值数据渲染。
- 同时链出一个 **headless CLI**：`simcore-cli replay --seed N --days 10`，CI 里跑确定性回归。

---

## 3. 决策（Decision）

> **⛔ 待用户拍板。** engineering-lead 的推荐是 **方案 E：`simcore`(C++20, 引擎无关) + Godot 4 表现层**。

**若采纳，一并生效的三条硬规则：**

- **R1 · 仿真/表现单向依赖**：`simcore` 不得 `#include` 任何引擎头；表现层不得写仿真状态（只能读快照 + 提交输入）。违反即在 CI 静态检查失败。
- **R2 · 时间只从 `simcore` 出**：表现层的 `delta` 只作为"累加器喂料"，不得用于任何判定、插值之外的逻辑（ADR-003 §4）。
- **R3 · 引擎选型可延后/可切换**：因为 `simcore` 是 C ABI 静态库，表现层切换（Godot → Unity → 其它）的成本被限制在 **桥接层（预估 1.5–2.5k 行）+ 面板 UI**，**不动任何仿真代码**。

**推荐理由（一句话）**：我们的难点是"确定性 + 可观测 + 低配"，不是"画面"；把仿真做成引擎无关的库，可以同时满足 K1（确定性可控）、K7（CI headless 回归）和 K8（小团队不被引擎绑死），而 Godot 4 的轻量正好匹配 GTX 1060 的渲染预算。

**若团队已有强 Unity 积累**：等价路径是 **方案 E′ = `simcore`(同一份) + Unity 6 表现层（P/Invoke 或 C++ 插件）**。对本项目而言，**`simcore` 的存在比引擎品牌重要一个数量级**；若必须在 Godot 4 与 Unity 6 之间二选一，请把选择依据限定为"团队熟练度 + 招人"，不要用技术理由互驳——因为仿真侧风险已被 R1/R3 隔离。

## 4. 后果（Consequences）

**正面**
- 确定性风险从"全局"收敛到"一个可在 CI 里 headless 验证的库"。
- 10 日重放回归可在无渲染下跑：14400 tick × ~0.02ms ≈ **数秒级**（见 ADR-003 预算），回归可进每次提交。
- 预算可剖分：`simcore` 计时与引擎帧计时天然分离，验收 5 可直接举证。
- 引擎升级/换引擎不波及仿真。

**负面 / 成本**
- 需维护 C ABI 桥接层与两套构建（simcore 的 CMake + 引擎工程）。**缓解**：CI 把 `simcore` 编成静态库，引擎工程只链库。
- 表现层与仿真层的**双份状态**（渲染插值 vs 仿真真值）需要显式同步协议（见 architecture.md §4.4）。
- C++ 迭代速度慢于 C#/GDScript；**缓解**：Core 期仿真代码量预估 8–15k 行，且变更集中在数据表与规则函数。
- Godot 4 的 3D 工具链较弱，**需在 Core 早期做一次渲染冒烟**（2×2km 地形 + 77 角色 + 昼夜色温）验证 K5。

**中性但必须记账**
- 选 Unity 的话，上述 R1/R2/R3 同样适用，只是桥接层换成 P/Invoke + Burst 边界；预算数字不变。

## 6. 知识缺口（Knowledge Gaps）

1. **Godot 4 具体版本与 GDExtension ABI 稳定性**：我的训练数据不能保证覆盖当前最新的 Godot 4.x。定版前需补 `docs/engine-reference/godot/VERSION.md`（版本号、GDExtension API 级别、C# 支持状态、已知导航/LOD 缺陷）。**不确定即标记，不臆造 API。**
2. **Unity 6 的 Burst 严格浮点模式与 `float` 确定性保证边界**：若最终选 Unity，需官方/实测证据，不能凭印象。
3. **Godot 4 在 GTX 1060 6GB 上的 2×2km 地形 + 昼夜光照实测**：需 Core 早期一次渲染冒烟，作为方案 E 的**放行闸门**。
