## 1. A-1 · 可分流 RNG —— **PASS**

**问**：能否提供按 `streamId` 分流、可存档/读档恢复的伪随机源？验收 6 要求 save/load 后 10 日差异 ≤5%。

**答**：能。见 **ADR-002**。要点：

1. `value = pcg32_at(FNV1a64(worldSeed ‖ streamId), absTick × 4096 + callSeq)` —— **无状态纯函数**，只依赖 `(streamId, absTick, callSeq)`。
2. 分流天然成立：不同 `streamId` 的 `seed64` 彼此独立派生，互不干扰；新增 `streamId` 不改变既有流的取值。
3. 存档恢复：只需 `worldSeed / absTick / 调用顺序`，**无需 per-stream counter**（比 S0 §C3 的字面要求更省，且结构性消除 §C7-2 的"counter 归零"风险）。仍保留 `streamIdRegistryVersion` 做版本护栏，不匹配即拒绝重放。
4. 跳步：用 LCG 的二进制幂（模 2^64 线性函数复合）实现 O(log n) 跳步，配 per-stream 缓存把热路径压到 O(1)。

**关键收益**：正因为是无状态纯函数，**FULL 与 COARSE 取值次数不同也不会错位**——这正是 A-3 成立的数学前提。

**待确认**：ADR-002 §7 的 Q1/Q2/Q3（counter 构造、§C3 措辞、`raw` 取整方式）。

## 2. A-2 · 离屏结算预算 ≤6ms —— **CONCERNS（修订后 PASS）**

**问**：≤120 实体（FULL ≤32）在 GTX 1060 6GB / 16GB RAM / SATA SSD / 1080p 下仿真 ≤6ms/帧；S2 自留 ≤3.20ms p95。需确认 LOD 切换抖动可接受。

### 2.1 为什么原判定是 CONCERNS

S0 §C3 的预算表：

| 项 | 预算 |
|---|---|
| FULL ≤40（行为树 + 连续量） | 40 × 0.09 = **3.60ms** |
| COARSE ≤80（统计近似） | 80 × 0.012 = **0.96ms** |
| 写队列 + 归因记录 | **0.50ms** |
| 余量 | **0.94ms** |

三个问题：

- **① 双重记账**：这张表已把 6ms 用满，但 S1 自留 ≤1.2ms（S1 §8-5）、S6 单日批处理 ≤1.5ms、S3/S4/S5/S7 尚未分配 —— 余量 0.94ms 装不下。
- **② 口径冲突**：`FULL ≤40` 与 S2 §8 的取舍声明（"默认策略为匿名 FULL 上限 16，总 FULL=32"）冲突；Core 验收 5 与任务硬约束也都是 **≤32**。
- **③ COARSE ≤80** 与"场内实体 ≤120、其中 actor 仅 77（16 有名 + 60 匿名 + 玩家）"不符，80 个 COARSE actor 不存在。

### 2.2 修订后的口径（ADR-003 §5，可直接替换）

| 口径 | 数值 | 判定 |
|---|---:|---|
| 每 `SIM_TICK` 仿真（1 Hz） | **3.387 ms**（其中 S2 = 3.148 ≤ 3.20 ✅） | ✅ |
| 每 `HOURLY_TICK` 增量（1/60 Hz） | **1.493 ms**（其中 S1 = 0.508 ≤ 1.20 ✅） | ✅ |
| **最坏单帧**（SIM + HOURLY 同帧） | **4.880 ms ≤ 6.0** | ✅ 余 18.7% |
| 日切帧 | 4.887 ms（批处理分片 ≤1.5ms/帧） | ✅ |
| 60fps 摊销 | **0.057 ms/帧** | ✅ 105× 余量 |
| 快进 8 游戏小时 | ≈18.7ms 总量（≤800ms，42× 余量） | ✅ |
| 仿真内存 / 存档 | ≤4 MB / <1 MB（SATA SSD ≈ <25ms） | ✅ |

**依赖的两个前提**：① `SIM_TICK = 1 Hz`（见 F-6 修正）；② `LOD_FULL_MAX = 32`（见 F-8）。

### 2.3 LOD 切换抖动是否可接受

**可接受**。三条证据：

- 滞回 120/150m 把切换频率压到"玩家跨越 30m 环带"的量级；
- 残余抖动由「1 游戏分钟内切换 ≥3 次 → 强制锁定 COARSE 60 游戏分钟 + 告警」（S0 §B7-3 + ADR-003 D5）兜底；
- 且经 F-7 修正后，`simLOD` 不再含视锥，抖动的**仿真后果**只剩"是否逐分钟细化"，随机序列完全不受影响。

**判定**：**修订 S0 §C3 后 PASS**。

## 3. A-3 · 边界 tick 补做判定 —— **PASS（可实现）** ⭐

**问**：S2 §4.4 要求 LOD 降级时判定锚定边界 `absTick` 而非"发现帧"，需确认可实现——**否则确定性论证不成立**。

**答：可实现。判 PASS。** 三条支柱 + 三条可断言不变式（详见 **ADR-003**）：

**支柱**
- **F1**：`absTick = dayKey×1440 + minuteOfDay` 全局可预测 → 边界时刻可在 `DISPATCH` 时**离线预计算**成有序数组（闭形式：`startMin + travelMin`，`travelMin` 来自静态烘焙的路程常量表）。
- **F2**：`rollCheck` 的值是 `(streamId, absTick, callSeq)` 的**纯函数**（ADR-002）→ 早算晚算一致。
- **F3**：FULL 与 COARSE 走**同一段 `processBoundaries` 代码**，唯一差异是"boundary 之间是否做逐分钟细化"，而细化路径**禁止发起随机判定**。

**不变式（CI 可断言）**
- **I1**：`makeSeedCtx` 第二参**永远是 `e.absTick`**，绝不传当前 tick → 静态检查命中数 = 0。
- **I2**：全局处理序 = `(absTick, actorIndex, seqInActor)`；逐 tick 路径与批量快进路径用**同一排序键** → 单测比对逐位相同。
- **I3**：`behaviorTreeTick` / `closedFormAdvance` 内 `rollCheck` 命中数 = 0。

**最强检验**：`fastForward(8h)` 的结果必须与连续 `simTick ×480` **逐位相同**（ADR-003 V5）。这条一过，A-3 就不再是"论证"而是"事实"。

**未消费边界的处理**：`nextBoundaryIdx` 在日切时必须等于 `boundaries.size()`，否则 assert（V8）。

**判定**：**PASS**。（这不是 FAIL，也不是 CONCERNS——它是本项目确定性论证中最扎实的一环。）

## 4. A-4 · 事件总线因果引用 —— **PASS**

**问**：`AttributionLink{step, causeRef, effectRef, actorIds[], dayKey}` 需要事件总线支持"事件携带因果引用"而不只是广播。

**答**：支持。见 **ADR-004**。要点：

1. **总线形态**：同步、有序、单线程、按 tick 分代。**不做**异步/跨线程/优先级抢占/延迟投递——每一条都会引入顺序不确定性。
2. **handler 只写写队列**，不直接改世界状态 → 事件顺序不改变世界状态，只改变入队顺序，而入队顺序由 `(priority, actorId, seq)` 决定（S0 已定）。
3. **`step` 语义收窄为「跨系统边界次数」**：`causeRef` 与 `effectRef` 的 `<system>` 段不同才 +1。这是 H1 隐患的堵法，也是让 S0 §C7-4「>3 即设计违规」可被机器验证的前提。
4. **`WriteQueueItem` 增加 `causeRef / sourceSystem`**（H2 隐患：日切批处理最易丢因果）。
5. **append-only**：不改旧 link，补偿用追加反向 link。
6. **闭合集**：把 Core 验收 1 的三跳连锁机械化为 `S1.zone.*remaining → S2.actor.*need → S2.actor.*schedule → S5.community.*safeDays`，作为 `UNATTRIBUTED == 0` 与 `step ≤ 3` 的**唯一机器判据**。

**判定**：**PASS**（需确认 ADR-004 §7 的 Q1/Q2/Q3）。

## 6. 新发现的 5 项（F-6 ~ F-10）

### 🔴 F-6 · S0 §B3.1 累加器 60× 量纲错误（BLOCKER）

```text
原文：acc += dtReal × TIME_SCALE   （TIME_SCALE = 60）
      while (acc ≥ 1 && steps < 4) { SIM_TICK(); acc -= 1 }
```
60fps → `acc += 1.0`/帧 → **60 tick/现实秒** → 1 游戏日 = **24 现实秒**。
但 S0 §B2 与 §B8-① 都写「1 游戏日 = **24 现实分钟**」。**相差 60×**。

**唯一自洽读法**：`SIM_TICK = 1 Hz`（§B2 自己写了「每 1 游戏分钟 = 1Hz」）。

**推荐修法（修 A）**：把累加器单位显式化为「游戏秒」，门槛改为 60：
```text
acc += dtReal * TIME_SCALE;                    // 单位：游戏秒；60 游戏秒/现实秒
while (acc >= 60 && steps < 4) { SIM_TICK(); acc -= 60; steps++; }
```
`TIME_SCALE` 数值与调试值 `{30,60,120}` **全部不动**。

**影响面**：若不接受修正，全部预算数字（ADR-003 §5）作废，且 S1 §3.3「水 −8 点/h → 12.5h 喝空」与"一天三升水"的自洽论证会在实装上表现为"20 秒喝空"。

### 🔴 F-7 · 视锥进入 `simLOD`（BLOCKER）

S0 §B3.2「升级 = 距离 < 120m **或在视锥内**」→ 玩家转头改变 `tickLevel` → 改变仿真路径：
- 重放必须额外记录相机 yaw/pitch 进 `inputs[]`；
- 即便记了，LOD 抖动让"同一 tick 的判定次数"剧烈变化，归因链解释成本爆炸。

**建议**：`simLOD`（即 `tickLevel(actorId)` 的返回值，**命名与三档取值不变**）剔掉视锥；视锥只进 `renderLOD`（表现层私有，不进契约、不进存档）。
配套收益：玩家转头只让"远处 NPC 变简模"，**不会**让他的作息改变 —— 这正是 P2「看得见的作息」要的。

### 🟠 F-8 · `LOD_FULL_MAX` 40 vs 32

S0 §D 写 40；Core 验收 5 写"full-behavior ≤40"但**任务硬约束写 ≤32**；S2 §8 取舍声明明确"总 FULL=32"。
**建议统一为 32**，理由：S2 自留 3.20ms 只有在 32 时才成立（40 时 S2 = 1.36+1.44+0.408+0.30 = 3.51ms，超支）。

### 🟠 F-9 · S0 §C3 预算表双重记账

见 §2.1。**建议整表替换为 ADR-003 §5 的表 A/B/C**（tick 分级口径 + FULL=32 + COARSE=44 + 给 S1/S3/S4/S5/S7 显式留位）。

### 🟠 F-10 · 数值表示未定

S0 §C7-3 只给禁令（禁 `double`、禁超越函数），没给替代。**已由 ADR-005 解决**：milli 定点（1/1000），33 个设计量全部精确表示，10 日价格递推与 double 偏差 <1e-3。

## 7. 评审总结与放行建议

**可以进入实现**，但**必须先签收 2 个 BLOCKER 的修法**（F-6 / F-7），因为它们改变了两个"数字前提"。

| 放行门 | 条件 |
|---|---|
| **G1** | F-6 修正批准（累加器改游戏秒单位） |
| **G2** | F-7 修正批准（`simLOD` 剔除视锥） |
| G3 | F-8（`LOD_FULL_MAX` → 32）确认 |
| G4 | F-9（S0 §C3 预算表替换）确认 |
| G5 | ADR-001 引擎选型拍板（**可延后**：`simcore` 引擎无关化使表现层选择不阻塞仿真实现） |
| G6 | ADR-005 定点数确认（**阻塞 `simcore` 第一行代码**） |

**风险最低的开工顺序**：`simcore` 的 L1 层（`Fixed` / `RngStream` / `EventBus` / `WriteQueue` / 时钟累加器）→ 这些不依赖 G1/G2 之外的任何设计裁决，且能立刻跑 ADR-002 的 V1/V2 与 ADR-005 的 V1/V2。
